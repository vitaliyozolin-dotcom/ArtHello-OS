# Резервные копии ArtHello v52

Копируется одна активная D1 SQLite БД ArtHello. Собственник запускает ручную
копию в «Настройки → Резервные копии» и видит состояние, расписание и историю.
Файлы дневника School, внешние документы и секреты сервера в эту копию не входят.

## Контейнерный worker R7

Worker использует тот же проверенный неизменяемый образ, что и приложение.
Python и backup-код входят в образ при сборке. На production-host не нужны
установка Python, systemd units, `sudo`, изменение владельцев файлов или
Docker socket внутри приложения. Установку выполняет защищённый release
consumer после проверки точного образа и источника БД.

| Ресурс | Worker UID 1000:GID 1000 | Приложение UID 1000:GID 1000 |
| --- | --- | --- |
| Существующий data volume, `/data` | Только чтение, `volume-nocopy` | Существующий доступ приложения |
| Новый volume `/var/backups/arthello-v52` | Чтение и запись, 1000:1000, 0700 | Не подключён |
| Новый volume `/var/lib/arthello-v52-backup-control` | Чтение и запись, 1000:1000, 0750 | Только чтение; соединение с Unix socket |
| Отдельный volume `/var/lib/arthello-v52-tochka-activation` | Не подключён | Только чтение |

Пустые новые volumes получают владельцев, режимы и seed-файлы копированием
содержимого из образа при первом подключении. Seed backup/control `.layout`
имеет режим 0444. Activation-каталог принадлежит 1002:1000 с режимом 0750,
его `.activation-volume-v2.seed` — 1002:1000, 0440; маркер записывает отдельный
ограниченный процесс UID 1002. Worker не получает этот volume. Несовпадение
владельцев, seed или прав останавливает установку; исправления прав существующих
production-файлов и root-контейнера для инициализации нет.

Worker запускается с UID/GID 1000, `--network none`, `--read-only`,
`--cap-drop ALL`, `no-new-privileges`, ограничениями памяти/CPU/PID и собственным
временным `/tmp`. Источник задаёт единственная настройка
`ARTHELLO_BACKUP_SOURCE_RELATIVE`, например `d1/<canonical-path>.sqlite`.
Реальный путь получают из production inventory активной D1 БД; первый найденный
SQLite-файл выбирать нельзя. Проверяются точный путь без symlink, UID источника,
отсутствие записи для посторонних и фактический read-only mount. Source/WAL/SHM
не исправляются и не изменяются worker.

```sh
python3 -I /opt/arthello-backup/worker.py
python3 -I /opt/arthello-backup/probe.py --require-initial-verified
python3 -I /opt/arthello-backup/probe.py --status
```

Probe возвращает exit 0 только после завершённой первой копии, при включённом
расписании, idle-состоянии и наличии последней проверенной копии в истории.
Результат содержит `schemaVersion`, `state`, `initialVerified`, `initialBackupId`,
`lastVerifiedBackupId`, `nextAt`, `historyCount`. Сам по себе запущенный контейнер
не подтверждает резервное копирование.

## Выполнение и расписание

- Первая копия запускается автоматически. Расписание становится доступным
  только после сохранённого успешного восстановления этой копии.
- Ежедневный запуск — 00:15 UTC (03:15 Москва). После перезапуска worker делает
  одну копию за пропущенный период; выполненный слот хранится в закрытом state.
  Неуспешная первая или просроченная суточная копия повторяется через пять минут.
- Ручной и автоматический запуск используют тот же фиксированный backup CLI.
  Durable admission и общий `flock` исключают параллельные задачи. HTTP 202
  означает принятую задачу; завершение подтверждается новой записью в истории.
  Повторный запрос во время задачи или пятисекундного окна получает HTTP 409.
- Прерывание процесса сохраняет незавершённый статус; после перезапуска он
  отмечается как ошибка. Первая и пропущенная суточная копии повторяются.
  Предыдущая успешная история сохраняется и не подменяет результат новой задачи.
- SQLite Online Backup API читает точный файл через `mode=ro`, с учётом WAL.
  Горячее `cp`, `immutable=1`, остановка приложения и запись в source не используются.
  Если SQLite не допускает read-only WAL, копия завершается ошибкой.
- Каждая копия проходит `integrity_check`, восстановление в отдельную SQLite БД
  и сравнение таблиц, количества строк и логического содержимого. Пробная БД
  удаляется. Только после успешного восстановления временный каталог атомарно
  публикуется с синхронизацией данных и manifest на диск.
- Каталоги копий имеют режим 0700, файлы — 0600. Срок хранения — 14 дней;
  удаление завершённых старых копий происходит только после успешной новой.
  Лимит backup CLI — 15 минут. В журнал попадает фиксированный результат без
  содержимого БД, секретов и сырых исключений.

Unix HTTP interface остаётся прежним: `GET /status`, `POST /create`,
`Host: backup.internal`, socket `control.sock` с режимом 0660. Приложение
использует существующие transport и проверку прав собственника. Worker не
принимает shell-команды, пути или параметры копирования через HTTP.

## Восстановление и границы

Повторная проверка сохранённой копии, без обращения к live source:

```sh
python3 -I /opt/arthello-backup/backup.py --verify /var/backups/arthello-v52/arthello-v52-YYYYMMDDTHHMMSSZ-ID
```

`verified` означает выполненную проверку восстановления SQLite. Запуск
приложения на восстановленных данных выполняется отдельно. Пакет не заменяет
live БД автоматически; восстановление проводят на остановленном целевом
контуре, без смешивания копии с прежними WAL/SHM.

Копии сохраняются на том же сервере. Вынос копий на другой сервер и уведомления
об ошибках расписания этим пакетом не реализованы. Secrets, в том числе ключ
расшифровки сохранённых credentials, этот пакет не экспортирует.

## Проверки кандидата

```sh
python3 -I -B deploy/v52/backup/test_backup.py
python3 -I -B deploy/v52/backup/test_worker.py
bash scripts/test/arthello-backup-container-docker-smoke.sh "$IMMUTABLE_IMAGE_ID"
```

Docker fixture обязателен на hosted CI после сборки именно публикуемого image ID.
Он проверяет реальные copy-up права, live WAL через read-only volume,
восстановление содержимого, существующий Node transport, конкуренцию ручных
запусков, singleton, restart/catch-up и изоляцию activation. Все его данные
временные. Проверки исходного Python без Docker не подтверждают эти свойства.

Production acceptance отдельно подтверждает точный D1 source, работающий worker,
первую восстановленную копию, ручную задачу из интерфейса собственника и manifest
следующего суточного запуска. Fixture restore time не является production RTO.

## Прежний host-пакет

`install.sh`, `install-bridge.sh` и systemd units сохранены для прежнего варианта.
Они требуют host root и не вызываются контейнерным R7 consumer. Одновременно
включать прежний timer и новый worker нельзя. `backup.py` и `bridge.py` сохранены
без изменения: worker повторно использует CLI, чтение истории и ограниченный
Unix HTTP handler, а управление systemd заменено своим scheduler.

Технические основания: [SQLite Online Backup API](https://www.sqlite.org/backup.html),
[Python sqlite3.Connection.backup](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup).
