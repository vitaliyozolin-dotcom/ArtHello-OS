# Этап 1: люди, роли и школьные справочники

Дата: 04.10.2026. Статус: **кандидат школьной части; этап целиком не принят и не опубликован**.

Основание: [ТЗ для дневника](https://docs.google.com/document/d/11BFb3A32CFUhGarFzfL2575dsF0km_HQJ0ovLxLISkI/edit), поручение владельца «Внедряй 1 этап».
Ветка: `codex/diary-stage1-20261004`, база: `c507327048fd9d07c31f7f50086a2168fedaebff`.

## Паспорт работы

- Цель: дать руководителю и администратору рабочие справочники и точки управления; сохранить единые карточки людей и разграничение доступа.
- Владелец решения: Виталий. Приёмка: владелец и ответственный за школу после публикации и проверки сквозных сценариев.
- Пользователи: директор, завуч, администратор; учитель, родитель и ученик получают только разрешённые данные.
- Источник людей, семей, состава классов и доступов: ArtHello OS. Локальные дубли людей, регистрация и выдача прав в дневнике остаются запрещены.
- Источник учебных настроек: дневник — предметы, назначения «педагог — класс — предмет», классный руководитель.
- За рамками этой поставки: новые сценарии КТП, массового расписания, оценок, посещаемости, событий и расчётов.
- Условие завершения этапа: проверены изменения в центральной системе и их доставка в дневник/Atlas, роли, интерфейс и рабочая публикация. Одна успешная сборка этого условия не выполняет.

## Реализовано в кандидате

1. Главная директора, завуча и администратора: переходы к людям, классам, предметам, назначениям, доступам и учебным разделам.
2. Предметы: создание, редактирование, архив и восстановление с сохранением стабильного ID и истории оценок. Архивирование при действующих назначениях, уроках или программах отклоняется.
3. Назначения педагогов: подтверждённый педагог, действующие класс и предмет; повторное сохранение не создаёт дубль. Снятие назначения с действующим расписанием/программой требует сначала изменить эти зависимости.
4. Классный руководитель: выбор подтверждённого педагога без изменения центральной карточки класса и состава учеников.
5. Люди: поиск по ученику/родителю; доступы: поиск, фильтры роли и статуса, переход в центральный модуль. Центральные ссылки принимают только четыре фиксированных раздела и не допускают произвольный redirect.
6. API: три управляющие роли, проверка текущего статуса и роли в транзакции, обязательный same-origin для записи, контроль версии и аудит в той же транзакции. Устаревшее окно получает 409.
7. Исправлено повторное заполнение справочников: старт приложения вставляет отсутствующие исходные записи и не перезаписывает сохранённые изменения.
8. Исправлена область видимости классов: учителю — назначенные классы, родителю и ученику — классы связанных детей.

Схема базы не меняется. Изменения данных не выполнялись на рабочей базе. GitHub Actions и инфраструктура не перенастраивались.

## Проверки

- `pnpm run build`: production-сборка Next.js и проверка TypeScript.
- После сборки `pnpm run test:directory:runtime`: 30 проверок запущенного приложения, отдельная временная SQLite, синтетические пользователи, случайные сессии. Проверяются восемь ролей, запрет записи с другого сайта, конфликт двух изменений, область видимости, редирект и сохранность изменений после остановки и повторного запуска.
- Полная команда `pnpm run test` включает новые тесты. Успешно: 95 из 95. [Протокол](acceptance/stage1-2026-10-04/build-and-tests.txt), [проверки приложения](acceptance/stage1-2026-10-04/runtime.txt), [машиночитаемый результат](acceptance/stage1-2026-10-04/result.json).

## Порядок выпуска и отката

1. Подтвердить актуальную версию на рабочем сервере и сопоставить её с базой этой ветки. Не накатывать поверх неизвестной версии.
2. Завершить центральные и браузерные проверки из таблицы выше.
3. Через существующий разрешённый канал выпуска включить обслуживание, выполнить согласованную SQLite backup с учётом WAL, проверить целостность копии и сохранить текущий артефакт.
4. Собрать и доставить этот commit штатным прямым способом. GitHub Actions не запускать по инструкции владельца.
5. Проверить вход и права ролей, сохранение предмета, назначения, классного руководителя, обновление после перезапуска и сквозную доставку центральной карточки. Только после этого отметить этап как принятый.
6. При ошибке вернуть предыдущий артефакт. Эта поставка не меняет схему; восстановление данных из копии допускается только после оценки записей, появившихся после backup.

Доступный сервер BV содержит только предыдущий неподнятый кандидат и staging-процесс центральной ОС; он не является подтверждённым каналом выпуска школы. Ранее прямой SSH-запуск к production был отклонён автоматической проверкой безопасности. Обход этого отказа через другой инструмент не выполнялся.
