# ArtHello Front Office — модель управляемых знаний

## Статус документа

Этот документ описывает смысловой контракт будущей базы знаний Front Office.
Он не является миграцией, не изменяет общую схему ArtHello OS и не разрешает
подключение реальных данных.

Текущий UI использует только синтетические объекты `DEMO`.

## Задача

База знаний должна отвечать не только на вопрос «что написано», но и на вопросы:

- для какого проекта, услуги и филиала действует правило;
- откуда получен каждый существенный факт;
- кто отвечает за содержание;
- кто утвердил публикацию;
- с какой даты действует версия;
- когда её нужно пересмотреть;
- какие исключения существуют;
- что разрешено выполнить автоматически;
- когда требуется человек;
- можно ли использовать знание в AI-черновике.

## Сущности

### `KnowledgeArticle`

Стабильная карточка темы.

Минимальные поля:

- `project_id`;
- `article_id`;
- `topic`;
- `owner_role`;
- `lifecycle_state`;
- `created_at`;
- `retired_at`.

Статья не содержит «текущий текст» напрямую. Содержание хранится в версиях.

### `KnowledgeVersion`

Неизменяемая версия содержания статьи.

Минимальные поля:

- `version_id`;
- `article_id`;
- `version_number`;
- `status`;
- `body`;
- `effective_at`;
- `review_at`;
- `service_scope`;
- `branch_scope`;
- `exceptions`;
- `allowed_actions`;
- `escalation_rule`;
- `response_template`;
- `created_by`;
- `created_at`.

После утверждения версия не редактируется. Исправление создаёт следующую версию.

### `SourceReference`

Ссылка на источник, из которого получен факт.

Минимальные поля:

- `source_ref_id`;
- `version_id`;
- `source_type`;
- `source_id`;
- `source_version`;
- `effective_at`;
- `retrieved_at`;
- `confidence_status`.

Старый диалог сотрудника не является политикой и не получает статус
`VERIFIED` без утверждённого источника.

### `VerifiedFact`

Отдельное проверяемое утверждение.

Минимальные поля:

- `fact_id`;
- `version_id`;
- `statement`;
- `source_ref_id`;
- `status`;
- `valid_from`;
- `valid_until`.

Допустимые статусы:

- `VERIFIED`;
- `PARTIAL`;
- `UNVERIFIED`;
- `CONFLICT`;
- `STALE`.

### `KnowledgeApproval`

Решение человека по конкретной версии.

Минимальные поля:

- `approval_id`;
- `version_id`;
- `approver_role`;
- `decision`;
- `decided_at`;
- `comment`;
- `evidence_ref`.

Автор версии и утверждающий должны быть различимы в аудите, даже если на раннем
этапе это один и тот же человек.

### `KnowledgeGap`

Зафиксированный пробел или конфликт знаний.

Минимальные поля:

- `gap_id`;
- `project_id`;
- `topic`;
- `reason`;
- `occurrence_count`;
- `source_ticket_refs`;
- `owner_role`;
- `due_at`;
- `impact`;
- `next_action`;
- `status`.

Причины:

- `MISSING_ARTICLE`;
- `MISSING_SOURCE`;
- `SOURCE_CONFLICT`;
- `STALE_POLICY`;
- `UNHANDLED_EXCEPTION`;

### `RetrievalRun`

Аудит того, какие знания были найдены для конкретного AI-черновика.

Минимальные поля:

- `retrieval_run_id`;
- `project_id`;
- `query_scope`;
- `article_version_ids`;
- `excluded_version_ids`;
- `exclusion_reasons`;
- `created_at`.

### `AIDraft` и `ClaimEvidence`

`AIDraft` хранит внутренний черновик. `ClaimEvidence` связывает каждое
существенное утверждение черновика с `VerifiedFact`.

Черновик без доказательства не получает разрешение на отправку.

## Жизненный цикл версии

```text
DRAFT
  → IN_REVIEW
  → APPROVED
  → STALE
  → RETIRED
```

Допустим возврат `IN_REVIEW → DRAFT` с комментарием проверяющего.

Запрещены переходы:

- `DRAFT → APPROVED` без решения утверждающего;
- редактирование `APPROVED`;
- возврат `STALE → APPROVED` без новой версии;
- автоматическая публикация AI;
- удаление использованной версии из аудита.

## Правило допуска знания к AI

Версию можно использовать только если одновременно выполнено всё:

1. `project_id = ARTHELLO`;
2. версия имеет статус `APPROVED`;
3. каждый используемый факт имеет статус `VERIFIED`;
4. версия вступила в силу;
5. дата пересмотра не просрочена;
6. услуга, филиал и дата обращения входят в область применения;
7. у клиента нет индивидуального договора с приоритетным условием;
8. действие не входит в запрещённую область;
9. доступ пользователя позволяет читать источник;
10. AI работает не выше `DRAFT_ONLY`.

Если хотя бы одно условие не выполнено, версия исключается из ответа, а причина
попадает в `RetrievalRun`.

## Приоритет источников

1. Текущее состояние конкретной услуги или записи.
2. Индивидуальный договор или принятая оферта.
3. Действующая политика.
4. AlfaCRM или другая операционная система-источник.
5. Платёжный и банковский статус.
6. Утверждённый каталог.
7. Утверждённая база знаний.
8. Публичный сайт.

Конфликт не разрешается выбором «удобного» источника. Создаётся
`KnowledgeGap` и задача владельцу.

## Изоляция и приватность

- все запросы содержат явный `project_id = ARTHELLO`;
- глобальный поиск по разным проектам запрещён;
- статья не должна содержать персональные данные клиента или ребёнка;
- персональные факты остаются в клиентском контуре и не становятся знаниями;
- права на чтение источника проверяются до формирования AI-контекста;
- аудит хранит идентификаторы источников, но не копирует лишние чувствительные
  данные.

## Отказ от AI

AI-функции являются необязательными.

При отказе:

- статьи, источники, задачи и ручной поиск продолжают работать;
- AI-черновики и AI-подбор знаний не запускаются;
- сотрудник использует тот же утверждённый контур вручную;
- ранее созданные аудиторские записи сохраняются по политике хранения;
- повторное включение требует явного разрешения.

## Решения перед реальной реализацией

До создания таблиц и API необходимо отдельно утвердить:

1. владельца миграций;
2. фактическое сопоставление с существующей схемой ArtHello OS;
3. роли владельца и утверждающего;
4. правила хранения версий и аудита;
5. права по филиалам и услугам;
6. способ ссылки на договор, AlfaCRM и каталог без копирования данных;
7. SLA для `KnowledgeGap`;
8. процесс экстренной блокировки ошибочной статьи;
9. QA-набор для проверки поиска и claim-level evidence;
10. rollback и импорт существующих документов.
