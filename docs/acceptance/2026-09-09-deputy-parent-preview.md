# Учебный кабинет руководителя: запрос владельца

Виталий согласовал рабочий кабинет заведующей учебной частью школы/сада «Атлас»: расписание, события, программы, обзор доступных классов и групп, учебный предпросмотр родителя. Разрешение на реализацию получено в чате; не считать его разрешением на доступ ко всем подразделениям.

## Факты аудита исходников

- Роль deputy уже включает редактирование расписания, создание событий, работу с программами и утверждение КТП. Это проверка кода, не подтверждение роли сотрудника в рабочей базе.
- visibleStudentIds для operationalRoles возвращает всех активных учеников текущего экземпляра; отдельной фильтрации по филиалу нет. assertTeacherScope также пропускает leadershipRoles без дополнительного scope. Нельзя назначать deputy сотруднику ограниченного подразделения до сопоставления контуров.
- loadSnapshot указывает «Школа 1–11», а модель использует school_classes и grade. Отдельная дошкольная модель не подтверждена. Не отождествлять «Атлас» с «1–11» без подтверждения.
- События используют текстовый audience; это не подтверждённая серверная фильтрация по подразделению.
- Настоящая роль и центральный ID сотрудника не прочитаны: защищённый рабочий доступ в этой сессии не получен. Роли и реальные данные не изменены.

## Подготовленный кандидат

Существующие директор/завуч выбирают ребёнка из своего текущего разрешённого списка. Сервер отклоняет неизвестного ребёнка без перехода на первого доступного. Ответ содержит только явный белый список учебных полей: расписание/задания класса, оценки, достижения, посещаемость ребёнка и комментарии visibility=parent. Финансы, сообщения, уведомления, приглашения и аудит не возвращаются. Поля staff snapshot не копируются автоматически.

Экран явно обозначен как учебная часть предпросмотра родителя. Это не полный пиксельный двойник семейного кабинета. Нет действий от имени родителя, смены серверной роли или пометки сообщений прочитанными. Запросы POST с preview отклоняются до инициализации данных. Уход по основной навигации закрывает предпросмотр. Методисту и администратору новый доступ не выдаётся: отдельные полномочия требуют scope.

## Приёмка и дальнейшая работа

- 4 новых проверки: отказ других ролей, отказ неизвестного ребёнка, исключение других детей/частных данных, серверные guards. Вместе с identity/design/structure — 39/39 PASS.
- Полная Next production build проверяется отдельно; visual/live acceptance остаётся открытой.
- До назначения роли: установить центральный ID сотрудника, фактическую роль, соответствие «Атлас»/«1–11», разрешённые филиалы/классы/группы; если контуры разные, сначала реализовать подписанный серверный scope и отрицательные межфилиальные тесты.
- Дошкольный контур отдельно: группы/возраст/план занятий, без автоматического переноса школьных оценок/КТП.
- Финальная приёмка: руководитель создаёт расписание → назначенный педагог видит занятие → связанный родитель видит опубликованный результат. Использовать изолированный fixture до проверки рабочих прав.
- Зависимость: кандидат поверх PR401, не заменяет выпуск кнопки возврата. Приоритет Точка → АльфаCRM сохранён. Production не изменён.


## Уточнение владельца — 2026-09-10

Запрос Екатерины Грудановой относится к школе и садику «Атлас». PR402 подготовлен в другом приложении и остаётся черновиком для возможного повторного использования; не выпускать его как выполнение запроса Кати. Проверки 39/39 и сборка относятся только к этому школьному кандидату и не доказывают готовность «Атласа».

В основной ArtHello уже есть раздельные константы:
- BR-ATLAS-SCHOOL — «Атлас — школа»;
- BR-KINDERGARTEN — «Атлас — садик»;

Источник: deploy/v52/src/lib/education.ts на main. Центральный вход и staff-sync привязаны к SYS-SCHOOL-1-11. Само наличие branch IDs не подтверждает отдельного рабочего дневника «Атласа» или права сотрудника в нём.
