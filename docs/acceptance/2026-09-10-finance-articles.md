# D108 — статьи и ручное разнесение: кандидат

Основание: поручение Виталия «Давай тогда перейдем к статьям и их разнесению» после подключения Точки. Владелец процесса — Виталий. Разработка разрешена; конкретные названия статей и назначения реальным платежам не считаются утверждёнными этим документом.

## Было и становится

В активном materialized v52 статья вводилась свободным текстом, предложения смешивали ДДС и ОПиУ. Сохранение проекции и аудита выполнялось двумя отдельными операциями, без проверки версии открытого платежа. Добавляется:

- единый справочник с отдельными статьями ДДС и ОПиУ, направлением и видом деятельности для ДДС;
- жизненный цикл «черновик → утверждена → архив»: финансовый сотрудник предлагает, руководитель утверждает; имя неизменно, удалений и массового переименования истории нет;
- выбор утверждённой статьи в карточке операции; сохранение ранее назначенного имени возможно, но не разрешает использовать его для других операций;
- фильтр «Без статьи» и точный фильтр по статье; ДДС по статьям с переходом в реестр и суммами в копейках;
- подбор похожих рублёвых банковских операций за выбранный месяц: точный ИНН И назначение содержит, только операции без статьи. Это предпросмотр, без сохранения/активации правила и без массовой записи;
- явное назначение класса, статьи и корректного календарного периода ОПиУ. Приход денег не создаёт клиентское начисление автоматически.

## Хранение и безопасность

Новый ключ `finance_article_catalog_v1` в существующей `system_runtime_state`: schema 1, revision, до 500 статей. Новый DDL, seed, SQL миграции или новые роли не нужны. Отсутствующий ключ означает пустой справочник; повреждённый ключ останавливает запись и не заменяется пустым. Финансовый источник и его данные не копируются в документы/fixtures.

Используется существующий `/api/finance-actions`, аутентифицированный контекст и матрица `lib/access-policy.ts`. Изменение каталога и назначения дополнительно проверяет CSRF. UI отправляет существующий CSRF cookie в заголовке. Клиентский `x-arthello-role` не является источником прав.

Обновление и аудит выполняются одним атомарным D1 batch. Каталог сравнивается с прочитанными bytes/revision; операция — с `updated_at`, который строго продвигается. Проигравший параллельный редактор получает 409, без записи и ложного аудита. Архивация статьи между чтением и записью также блокирует устаревшее разнесение. Ошибка аудита откатывает весь batch. Поля `bank_transactions`, сумма/дата/направление/юрлицо/ссылка банка в `financial_operations` не входят в разрешённый UPDATE.

Начисления AlfaCRM, закрытие месяца, автоматическое применение правил, ИИ-классификация и массовое изменение реальных операций не включены в этот этап. Никаких внешних AI-запросов, платежей или платных сервисов. Отказ от работы со справочником сохраняет банковский импорт и прежнюю историю; новые операции остаются без статьи до явного разнесения. Цена инфраструктурного запуска неизвестна; метрика этапа — доля операций с явно утверждённой статьёй при неизменных банковских суммах.

## Предложение для справочника — не seed и не утверждённые данные

| Блок ДДС | Кандидаты названий | Разнесение |
| --- | --- | --- |
| Операционные поступления | Оплата школы; оплата детского сада; дополнительные занятия | Вид услуги подтверждается документом/назначением. Плательщик не считается конкретной семьёй без связи с CRM. |
| Операционные выплаты | Выплаты педагогам; выплаты другим сотрудникам; аренда; коммунальные услуги; продукты питания; учебные материалы; хозяйственные расходы; реклама; ИТ и связь; банковские комиссии; налоги и взносы; возвраты клиентам | Зарплата и налоги требуют отдельной детализации; ИНН одного контрагента может соответствовать разным статьям. |
| Инвестиционная деятельность | Покупка оборудования; капитальные улучшения | Не относить всю оплату автоматически в расходы ОПиУ. |
| Финансовая деятельность | Получение займа; возврат основного долга; вклады собственника; выплаты собственнику | Основной долг и финансирование не превращаются в выручку/расход ОПиУ. Проценты выделяются отдельно. |
| Внутренние переводы | Перевод между своими счетами: поступление; перевод между своими счетами: списание | Название статьи не доказывает парность: автоматического сопоставления или исключения оборотов на этом этапе нет. |

Филиал, юрлицо и контрагент — отдельные измерения. Не создавать копию каждой статьи под каждый банковский счёт. ОПиУ ведёт отдельный справочник доходов и расходов; его названия/периоды не выводятся автоматически из этой таблицы.

## Проверки и приёмка

RED: новый behavioral suite отказал при отсутствии `lib/finance-articles.ts`. GREEN: модель, транзакционный SQLite port и actual route boundary. Проверяются отсутствие seeds, нормализация дублей, права, CSRF, направление/отчёт, календарный период, сохранение legacy, конкуренция, архив между чтением/записью, rollback при недоступном аудите, неизменность банковского факта, точные копейки, AND/ИНН/месяц/неразнесённые в предпросмотре. Existing finance suites остаются.

Локальный запуск части старых integration suites ограничен отсутствием TypeScript/Miniflare. Сборка, lint и полный v52 glob требуют hosted application stage. UI ещё требует проверки на узком экране и полного create → approve → classify → reload → DDS drilldown в изолированном браузере.

Production-приёмка этого этапа пока НЕ выполнена. Последний принятый runtime — R16. Нельзя выдавать PR, тесты или сверку банка за установленный справочник. Новому runtime потребуется отдельный штатный protected release с сохранением всех старых receipts/истории/backup и запретом восстановления старой базы после публичной границы.

## Унаследованный блокер проверки исходников

Уже на исходном main `1bfe6634bf1a0e90ae20c64cbf428d9cd3358549` Quality run `34473673544`, job `102859227193` отказал: manifest ожидает v44 `fe986d777462b383af173fca83fe1760cad02f25659c147f9ca92671bb3e4640`, фактический canonical tar `164da587ce0e07d35e3696ddfda53f4cd372a63e38365dad52fb3c6966d711df`. Тот же результат воспроизведён локально. Все 238 v44 Git blobs и executable modes по authoritative main сопоставлены с рабочими bytes; v44 исходники не меняются. Исправляется manifest фактического version-controlled дерева. Причина появления прежнего значения у автора D105 не установлена; оно не соответствует сохранённому main. Canonical algorithm и отрицательные проверки content/extra/missing/executable сохраняются. v52 manifest обновляется на явную дельту этого кандидата; frozen release inputs не переопределяются.

Ревизия выявила дополнительную границу положительных сумм ОПиУ: новое назначение дохода списанию (или расхода поступлению) отказано, чтобы не завысить итог. RED воспроизведён как Missing expected exception; добавлен явный guard. Legacy сохраняется только при полном сохранении прежнего класса/статьи/периода. Возвраты разносить в ДДС; корректировки ОПиУ требуют отдельной реализации и не имитируются отрицательным банковским фактом.

## История выпусков после изменения product source

Унаследованные continuation-проверки R14/R15/R16 отказывали на source drift уже после D105. Они больше не могут объявлять новый продуктовый source старым release source. Новый hosted-only `run-accepted-r16-history.py` сначала проверяет текущий canonical source и 64 поведенческих банковских/финансовых теста, все 97 текущих R16 входов и неизменённый production controller. Единственные три изменённых входа закреплены отдельными SHA: текущий manifest, ранее изменённые D105 Dockerfile и `tochka-autosync.ts`. В последнем D105 убрал повторный `failureStage === sync_commit` при записи результата; observer уже обнуляет kind для других стадий. Эта строка не изменяется D108, текущие scheduler tests выполняются.

Старые команды R14/R15/R16 полностью исполняются в отдельном локальном checkout точно принятого `cb990279e070fddbfa9a0adbd21b56de25b85588` / tree `1ce4c733034060dc84d558d49dab96d1be9b1cf8`. Это historical fixture, не кандидат production; результат явно `production_acceptance=not_run`. Новый helper проверяет внешний SHA до/после, pinned исходники и весь verification workflow; тесты отказывают для каждого из 97 изменённых входов, altered pins/controller/workflow, произвольного suite и другого внешнего SHA. Frozen helpers/pins/controllers не редактируются; ни одна старая успешная установка не перезапускается.

Workflow hygiene: изменяется один существующий verifier, число его jobs остаётся 5; triggers PR/push, hosted ubuntu-latest, contents:read, checkout exact SHA/depth0/credentials:false и прежняя concurrency сохраняются; environment/secrets/self-hosted/production actions не добавляются. Production R16 по-прежнему принимает только свой исходный PR/prefix; общий legacy v44 deploy не затронут.
