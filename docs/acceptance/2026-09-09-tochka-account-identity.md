# Точка: идентичность операций по счёту — D-097

Статус: проверено на синтетических данных; выпуск в production и банковская приёмка ещё не выполнены.

## Подтверждённая проблема

Нормализованный `bank_transactions.id` уже включает счёт и идентификатор операции провайдера. Идентификатор финансовой проекции включает юридическое лицо, счёт и операцию. Однако фактический SQLite-индекс R13 `bank_transactions_provider_unique` ограничивает только `(connection_id, provider_transaction_id)`. При одинаковом идентификаторе провайдера на разных счетах первая пачка операций откатывается целиком, хотя счета и выписки уже записаны предыдущими пачками.

Это воспроизведённый дефект кода, а не установленная точная причина производственного исключения. Наблюдение 2026-09-09 17:30:05 UTC подтвердило этап `sync_commit`, 4 счёта, 12 READY-записей выписок и 0 банковских / финансовых операций. Все необходимые поля семи таблиц присутствуют; неожиданных обязательных полей, триггеров и внешних ключей нет. Текст исходного исключения не сохранялся. Следующий штатный запуск — 22:01:53 UTC, backoff не изменён.

Источник наблюдения: [D075 run 34383175602](https://github.com/vitaliyozolin-dotcom/ArtHello-OS/actions/runs/34383175602), job 102572786192. Диагностический source `4289828c8eefe074d95c4a8510c957ea3c287ede`; подтверждённый live source R13 `f5fa3e46e3510e6fc98ae4455f4b499c0ba30695`.

## Domain mini-spec

| Объект | Ключ / связь | Изменение |
| --- | --- | --- |
| Счёт банка | connection + provider account | Нет |
| Операция банка | PK id из account + provider transaction; unique connection + account + provider transaction | Уникальный индекс согласован с уже существующим ключом строки |
| Финансовая операция | id из legal entity + account + provider transaction; bank financial_operation_id → financial id | Нет |
| Данные провайдера | source_payload_hash, provider IDs, statement ID, сумма в копейках, направление, дата | Не переписываются миграцией |
| Ручная классификация | Отдельные поля финансовой проекции | Не переписываются миграцией |
| Состояние автозагрузки | Существующий JSON system_runtime_state | Только фиксированный commitFailureKind при ошибке sync_commit |

Банк остаётся источником фактического движения денег. Эта правка не импортирует XLSX/CRM, не объединяет контрагентов и не создаёт платежей. Новых таблиц и FK нет. Период, company/account scope, правила рублёвой проекции, lease, credential-generation fence, pause, расписание и backoff сохранены.

## Migration review

Применимость: работающий v52 использует SQLite/D1 из `deploy/v52/overrides/db`. PostgreSQL-схемы `lib/db/src/schema/{banking,finance}.ts`, barrel exports, Drizzle journal и D-036 проверены для разграничения контуров; они не описывают текущую live-базу. PostgreSQL journal/snapshot, rollback SQL и TEST_DATABASE_URL twin: SKIPPED — этот контур не изменяется.

Bootstrap распознаёт только отсутствующий индекс, точное старое определение либо точное новое определение, включая unique, partial, origin, порядок, направление и BINARY collation. Неожиданное определение останавливает запуск с фиксированным кодом. Старый индекс заменяется двумя DDL-командами в одной транзакционной D1 batch. Строки не удаляются и не обновляются. Повторный bootstrap ничего не меняет. Обычный CREATE IF NOT EXISTS согласован с новым определением; второго обходного индекса нет.

При ошибке создания транзакция возвращает старый индекс. Откат к коду R13 сохраняет расширенный индекс с прежним именем: его CREATE IF NOT EXISTS не сужает scope. Автоматически возвращать старую уникальность после импорта нельзя, поскольку корректные операции разных счетов могут разделять provider ID. Production-выпуск требует штатной проверенной резервной копии и существующего защищённого rollback контура; копия здесь не заявлена как уже созданная.

## Проверки

29 тестов PASS: 7 новых SQLite/commit регрессий и 22 существующие проверки планировщика/реального собранного route. Исходный дефект воспроизведён до миграции; после неё синтетические 4 счёта × 2 операции дают 8 банковских и 8 финансовых строк, 4000 коп. прихода / 1200 коп. расхода, все связи существуют. Повтор даёт 0 новых финансовых строк. Проверены сохранность строк, запрет дубля в одном счёте, идемпотентность, отказ при неизвестном индексе и транзакционный откат ошибки CREATE. Синтетические суммы не являются результатом реального банка.

Классификатор читает максимум три вложенных Error с сообщениями до 4096 символов; в состоянии сохраняется только фиксированная категория. Произвольный текст, реквизиты и банковский payload не сохраняются. Проверены исключение исходного объекта, очистка причины после успеха и прежняя задержка повтора.

Для неизменных старых проверок v52 восстановлены только исторические YAML-входы из принятого R13 в отдельной временной папке; активные workflow не восстанавливаются. Проверка действующего verify-v52 YAML остаётся над текущим файлом. Все не-YAML файлы исторических контрактных тестов берутся из точного проверяемого HEAD, затем образ собирается из повторно очищенного точного checkout. Новая регрессия выполняется в hosted verify-v52 после immutable upload.

## Осталось

Пройти hosted сборку и release gates, выпустить отдельный защищённый релиз, затем прочитать реальное состояние и проверить 4 счёта, актуальный период, количество и суммы операций, связи с ДДС и отсутствие дублей. До этой проверки задача Точки остаётся открытой.
