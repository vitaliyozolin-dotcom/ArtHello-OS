# D189: единая идентификация — кандидат

## Что изменяется

- Существующий ID ОС остаётся основным. `(entity_type, source_system, source_record_id)` сохраняет уникальность источника; `entity_merges.duplicate_id` имеет уникальный индекс и ведёт к каноническому корню, включая цепочки старых подтверждений.
- Филиалы хранятся как назначения с исходным ID карточки и признаком активности. Подтверждённая семья может содержать нескольких детей; дети не объединяются вслед за семьёй.
- Автоматическое подтверждение ограничено одним объектом AlfaCRM с взаимным подтверждением филиалов в текущем полном снимке. Разные ID, слабые контакты, конфликтующие сведения и разные подтверждённые корни не дают автоматического слияния.
- Смена аккаунта при имеющихся партиях другого аккаунта блокируется до импорта. Исходные наблюдения и ссылка на партию остаются доказательством; семейная гипотеза по телефону не становится доказательством.
- В импортёре сохраняется статус ссылки. Назначения детей и учителей адресуются основным ID; старые ID учебных назначений не удаляются. Одновременные импорт, архив и ручное подтверждение сериализованы.
- Семейная карточка открывается по основному или старому ID, собирает детей, документы и историю по подтверждённым ссылкам. Остатки по филиалам не суммируются. HR скрывает карточки-ссылки из списка людей, сохраняя связь с источником истории.

## Авторизация и данные

Ручное подтверждение использует существующий `/api/entity-merge`: реальная сессия, origin, CSRF, роль/модуль реестра; для не-владельца необходимы текущие права на все филиалы обоих наборов карточек. Запись решения, проекция и аудит входят в одну транзакцию. Финансовые права и ограничения филиала в `/api/families/alfacrm-balances` проверяются отдельно. Root `quality-gates/permission-matrix.json` относится к старому Express API и не считается доказательством этих v52-проверок.

DDL и PostgreSQL-модели не меняются. В `lib/db/src/schema/persons.ts` имеется другая PostgreSQL-модель persons; она не выдаётся за production v52. Новый слой использует текущие v52 `entities/entity_merges`, а не создаёт вторую конкурирующую базу людей. Общая личность между разными типами карточек (родитель и сотрудник) остаётся отдельным подтверждаемым случаем.

## Выпуск и сверка

1. Пройти hosted Quality, Proof и Verify v52 на финальном SHA и сохранить резервную копию центральной SQLite с WAL. Старый D182 one-shot не является механизмом выпуска D189.
2. После проверенного выпуска выполнить полный контролируемый импорт семей, сотрудников, групп с закреплённым аккаунтом/филиалами. Сверить основные активные ID отдельно от ссылок, архивных исходных карточек и числа назначений. Не подгонять под оценку 200.
3. Повторить тот же снимок: основные ID и число людей стабильны, чужие филиалы не возвращаются, локальный архив сохраняется. Конфликты разных ID решать по документам через реестр, не по одному телефону.
4. Только после этого включать фоновый цикл D187 и проверять передачу основных ID в оба дневника; оценки/ДЗ/КТП не объявлять проверенными без ученика и урока в каждом.
5. При откате сначала остановить автоимпорт: старая версия не понимает новое разрешение ссылок. Восстанавливать согласованный backup приложения/БД; raw и историю не удалять ручной чисткой.

Описание формата AlfaCRM сверялось с [официальной документацией API](https://alfacrm.pro/usefull/integrations/integration/api); фактическое количество активных семей и остатки берутся только из проверенного конкретного снимка.

### Найденный блокер действующих доступов

`family_system_access` и payload `family-access-sync.ts` сохраняют исходные family/principal ID, `app_users.id` может совпадать с ID сотрудника. Обновлять эти личности без согласованного изменения получателей нельзя. Такие подтверждения теперь откладываются с аудитом `identity.source_alias_deferred`, пометкой «Требует сверки» и 409 при ручной попытке. История `hr_accesses` тоже защищена. Это конкретная незавершённая часть переноса в оба дневника, а не скрытое автоматическое изменение учётной записи. Блокер нельзя обходить удалением доступов или повтором password-reset событий.

Заключительное уточнение: ID клиента AlfaCRM не даёт права объединить по-разному названных представителей. В таком случае ребёнок/исходная семейная карточка могут иметь единый ID, но представители остаются отдельными и требуют сверки (`guardian_identity_conflict`). Отдельные проверки этого случая и обычного объекта нескольких филиалов: 2/2 PASS.

Проверка расширения филиалов сначала воспроизвела смену основного ID (RED). Исправлено: импорт запоминает опубликованные ID до создания новых проекций; ранее подтверждённый корень имеет приоритет. Добавление второго филиала и предварительно отдельно импортированной третьей копии теперь сохраняет исходный ID (2/2 PASS; связанный набор 4/4 PASS). Это не выбор по имени, телефону или дате создания.
