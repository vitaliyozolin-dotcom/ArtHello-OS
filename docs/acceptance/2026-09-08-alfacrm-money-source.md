# AlfaCRM: источник денежных остатков — 2026-09-08

Изолированный кандидат подготовлен относительно `c9e7da06f7d3637c0032af542085f28acb02816a`. Сохраняется изменение другого автора: импортный флаг читается лениво через `alfaCrmImportEnabled()`.

## Причина

[Официальная документация AlfaCRM REST API](https://alfacrm.pro/usefull/integrations/integration/api) определяет `Customer.balance` как деньги, а `paid_lesson_count` — как занятия. Денежная единица `CustomerTariff.balance` не подтверждена. Для платежей документировано поле `Pay.income`, но подтверждённой связи ID типа со списанием или поступлением не найдено. Прежние умножение остатка абонемента на 100 и классификация типов 5/12 не имели достаточного основания.

## Изменение

- Этап абонементов и остатков по-прежнему выбирается отдельно после семей, только в сопоставленных филиалах. Пакет содержит не более 15 уже импортированных клиентов. Для каждого заново читается `customer/index` с точным фильтром ID; чужой или избыточный ответ останавливает пакет до записи.
- Новый денежный снимок создаётся исключительно из свежего поля клиента. Занятия сохраняются отдельно, неизвестное значение — NULL. Точность денежных сотых проверяется без округления; дополнительные знаки, нечисловые и отсутствующие значения отклоняются. Валюта не угадывается, суммы разных филиалов не агрегируются.
- Неизменённые ответы клиента и абонементов сохраняются внутри неизменяемого наблюдения с контрактом `customer-balance-v2`. Его ID имеет отдельное пространство имён; старые ID абонементов не пересекаются с ним.
- Добавлена SQLite-таблица `alfacrm_customer_balances`: ключ `(remote_branch_id,customer_id)`, зафиксированный при импорте `local_branch_id`, семья, `balance_minor`, отдельный nullable `paid_lesson_count`, `source_field='Customer.balance'`, хеш и время сохранения. Строка lineage указывает на точное неизменяемое наблюдение.
- Старая таблица абонементов и её данные сохраняются. Новые деньги туда не пишутся. Если очередной денежный остаток не подтверждён, сохраняется последний подтверждённый снимок с прежней lineage. Потребитель должен показывать его время и учитывать последнее неуспешное обновление, текущую привязку филиала и права.
- Финансовый этап сохраняет исходные ответы в выбранном диапазоне, но блокирует денежную проекцию до подтверждённой карты типов платежей. `projectionBlocked=true`, статус этапа — ошибка, токен закрывается, watermark успеха не меняется. Это действует и для пустого ответа: отвергнутые записи не выдумываются. Прежние проекции и банковский ДДС не изменяются.
- Предпросмотры старого денежного контракта перестают разрешать импорт. Срок предпросмотра, последовательная обработка запросов, CSRF, владелец ключей, назначение интеграции и проверка филиалов сохраняются.

## Границы приёмки

Это проверка исправления источника, не доказательство выполненной синхронизации настоящего аккаунта. Запросов в аккаунт AlfaCRM, включения импорта, фонового расписания, публикации или изменения prod этой задачей не выполнялось. Перед денежными проводками нужны подтверждённая карта PayType и валюта; для реального импорта — действующие разрешённые ключи и проверка выбранного филиала.
