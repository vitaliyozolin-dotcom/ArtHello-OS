# Точка: автоматическая синхронизация v52

Статус: кандидат, не опубликован. База — сборка исправлений PR #351 с устойчивыми pending statement IDs и credentialGeneration.

## Поведение

- Node runtime вызывает внутренний `Miniflare.dispatchFetch` через 30 секунд после готовности, затем раз в минуту после окончания предыдущего вызова.
- Исполнитель строго ограничен `INT-T-TOCHKA`, уже сохранёнными JWT/customerCode/юрлицом/датой начала и разрешёнными банком счетами. Входное тело запроса не выбирает действие, интеграцию или платёж.
- Ключ служебного вызова — случайные 32 байта при старте процесса. Он остаётся в памяти Node/workerd, не возвращается клиентам и не сохраняется в Git, БД, env-файлах или журналах.
- Расписание использует сохранённые интервалы 60/180/360/1440 минут и минуту запуска; отметки времени — UTC. Ожидающая выписка повторяется через 5 минут, занятый ручной импорт — через минуту, ошибка — через 15/30/60/120/240 минут, максимум раз в 6 часов.
- Состояние расписания хранится в существующей `system_runtime_state`. Атомарная аренда и поколение ключа защищают от параллельного выполнения и устаревшего завершения. Новый ключ получает новое расписание.
- Явная пауза и удаление/замена ключа блокируют дальнейшие запросы и запись через SQL-проверку statement lease. Статус «Ошибка подключения» допускает ограниченный повтор: существующий импорт выставляет `is_enabled=0` и при временном отказе банка.
- «Возобновить» для Точки проверяет сохранённую подтверждённую привязку; больше не ищет отсутствующее в фактическом статусе слово «активна».
- Неполная выписка не обновляет `last_success_at`. Последнее успешное время сохраняется при последующей ошибке. Отклонённые строки получают задержку повторения как ошибка, а не частый pending polling.
- Автозагрузка использует прежние лимиты адаптера (45 секунд, максимум 200 счетов/20 000 строк на выписку), устойчивые provider IDs, fence и идемпотентную запись PR #351. Платёжные методы по-прежнему запрещены отдельным Node-транспортом.

## Включение в общий релиз

1. Скопировать четыре файла `deploy/v52/overrides/{lib/tochka-autosync.ts,production/tochka-autosync-timer.mjs,scripts/patch-tochka-autosync.mjs,tests/tochka-autosync.test.mjs}`.
2. В сборочной последовательности выполнить `node /app/scripts/patch-tochka-autosync.mjs` **после** `patch-tochka-pending-lifecycle.mjs` и после старого проверочного checksum `db/index.ts`. Patch проверяет точность исходных фрагментов и идемпотентен.
3. В финальном Docker stage добавить `COPY --from=application /app/production/tochka-autosync-timer.mjs /app/production/tochka-autosync-timer.mjs`.
4. Установить `TOCHKA_AUTOSYNC_ENABLED=1` **только для целевого production-контейнера после разрешённого cutover**. В clone/preflight/sandbox эту переменную оставлять отсутствующей либо `0`: восстановленная база не должна обращаться к реальному банку.
5. В общий release decision включить служебную аутентификацию, работу по расписанию и восстановление после временных отказов. `quality-gates/permission-matrix.json` проверен: он описывает отдельный legacy Express runtime; этот patch не изменяет его маршруты. v52 остаётся защищён proxy и отдельными behavioral-проверками служебного доступа.

## Проверки кандидата

- Новые behavioral tests: служебный ключ/метод/путь, сохранённые настройки и даты, расписание, параллельные работники, перезапуск, pending, backoff, ошибочный успешный HTTP-ответ, отклонённые строки, пауза до/во время выполнения, поколение ключа, истёкшая аренда, отзыв credential, lifecycle runtime-таймера, фактический integration-actions route и поддельный ключ.
- Существующие проверки Точки включают SQL-идемпотентность финансового реестра, сохранение ручной классификации, customer scope, credential rotation, pending statements и запрет платежных методов.
- ESLint затронутых файлов пройден.
- Сборка итогового образа и проверка живого production выполняются общим release-процессом; здесь они не заявлены.

## Живая приёмка без раскрытия ключа

1. Подтвердить штатный production SHA/image и отсутствие включения scheduler у clone.
2. Владелец видит сохранённую Точку: существующее юрлицо, подтверждённую компанию, выбранную дату начала, расписание. Для уже настроенной интеграции новый ввод ключа не требуется.
3. Без открытой страницы/ручной кнопки появляется `integration_sync_runs` с инициатором `SYSTEM:TOCHKA_READONLY_SCHEDULER`; в журнале runtime — только безопасный `TOCHKA_AUTOSYNC_TICK` результат.
4. Число счетов и банковские факты сверить с банком; провести сверку операций, суммы и количества за выбранный период. «Успешно» допустимо только при полном импорте без отклонённых строк.
5. Повторный автоматический запуск не создаёт вторых финансовых операций и не сбрасывает ранее выполненную пользователем классификацию. Pending сохраняет provider statement ID между попытками.
6. Пауза прекращает автоматические вызовы; возобновление восстанавливает выполнение. Отзыв ключа не оставляет рабочий банковский доступ.

Ограничение существующей модели: одна текущая настройка `INT-T-TOCHKA` относится к одной подтверждённой компании/юрлицу и всем её разрешённым счетам. Этот patch не создаёт несуществующие дополнительные подключения для других юрлиц. Распределение неоднозначных операций по филиалам остаётся ручным и не подменяется предположением.
