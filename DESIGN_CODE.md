# ArtHello OS Design Code 1.2.0

**Статус:** обязательный стандарт проекта  
**Исходная версия утверждена владельцем:** 27 августа 2026 г.  
**Уточнение области утверждено владельцем:** 28 августа 2026 г.  
**Компактная типографика утверждена владельцем:** 28 августа 2026 г.  
**Компактные KPI операционных реестров утверждены владельцем:** 28 августа 2026 г.  
**Область действия:** основная ArtHello OS и модули, для которых нет отдельного утверждённого продуктового дизайн-кода.

Этот документ является единственным источником истины по визуальной системе и поведению интерфейса в указанной области. Любой новый раздел, экран, компонент или изменение существующего интерфейса обязаны соответствовать этому стандарту либо явно указанному продуктовому дизайн-коду.

Отклонение допускается только после отдельного явного решения владельца. Локальные CSS-заплатки, новые параллельные дизайн-слои и исключения без зафиксированного решения запрещены.

## 1. Назначение и характер интерфейса

ArtHello OS — единая операционная система образовательной группы, а не CRM, набор отчётов или декоративный дашборд.

Интерфейс должен быть:

- спокойным и управленческим;
- чистым и современным;
- одинаковым во всех разделах;
- просторным, но не пустым;
- понятным сотруднику без отдельного обучения;
- функциональным при нулевом количестве данных;
- отдельно спроектированным для мобильного устройства, а не уменьшенной десктопной страницей.

### Эталонные экраны

- **Десктопная типографика, плотность, размеры текста и визуальная дисциплина:** раздел **«Доступы»**.
- **Мобильные внешние отступы, ритм, геометрия и читаемость:** раздел **«Обучение»**.
- **Цветовая идентичность:** действующая фирменная фиолетовая палитра ArtHello.

Все остальные экраны приводятся к этим эталонам.

Все размеры и цвета задаются семантическими токенами. Компоненты не должны содержать случайные локальные значения, если для них существует системный токен.

### 2.2. Радиусы

| Элемент | Радиус |
|---|---:|
| обычная карточка | `22px` |
| крупная панель / модальное окно | `28px` |
| поле / кнопка / селектор | `16px` |
| маленький статус | `12px` |
| круглая кнопка | `50%` |
| pill | только статус, тег или фильтр |

Запрещено:

- использовать случайную смесь `8 / 14 / 18 / 20 / 22px`;
- превращать обычные карточки в вертикальные или горизонтальные капсулы;
- создавать отдельную рамку вокруг заголовка, пояснения и каждого текста внутри одной карточки;
- сочетать квадратные KPI с округлыми карточками на одном экране.

### 2.3. Шкала отступов

Используется только системная шкала:

`4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64px`

Основные значения:

| Назначение | Размер |
|---|---:|
| мобильный отступ страницы от края | `20px` |
| планшетный отступ | `28px` |
| десктопный отступ | `32–40px` |
| внутренний отступ обычной карточки | `20px` |
| внутренний отступ крупной панели | `24px` |
| расстояние между карточками | `16px` |
| расстояние между крупными секциями | `24px` |
| заголовок → описание | `8–12px` |

Ни один текст, KPI, иконка или кнопка не должен прижиматься к краю контейнера.

### 2.4. Тени

Тень используется сдержанно:

- обычные карточки — без тени либо очень мягкая тень;
- модальные окна и плавающие панели — умеренная тень;
- вложенные элементы одной карточки не получают отдельную тень.

## 3. Типографика

Используется один UI-шрифт — тот же, что применяется в эталонном разделе «Доступы». Другие UI-шрифты внутри системы запрещены.

### 3.1. Мобильная типографика

| Элемент | Размер / line-height | Вес |
|---|---:|---:|
| заголовок страницы | `38 / 42px` | `700` |
| большой показатель | `28 / 32px` | `700` |
| заголовок секции | `22 / 28px` | `650–700` |
| заголовок карточки | `18 / 24px` | `650` |
| основной текст | `16 / 24px` | `400` |
| подпись поля | `14 / 20px` | `600` |
| вторичный текст | `14 / 20px` | `400` |
| текст кнопки | `16 / 20px` | `600` |
| статус / тег | `13 / 18px` | `600` |

### 3.2. Компактная типографика карточек

Эталоном компактной карточки являются шаги раздела «Доступы»: «Вход в ArtHello OS» и «Синхронизация дневника».

| Семантическая роль | Размер / line-height | Вес |
|---|---:|---:|
| заголовок компактной карточки | `12 / 15px` | `500` |
| краткое пояснение | `10 / 14px` | `400` |
| порядковый номер | `9 / 12px` | `800` |

Эта шкала обязательна для одинаковых смысловых ролей ArtHello OS: компактных инструкций, строк карточного списка и встроенных пустых состояний рабочего блока.

Это семантическое исключение из минимального размера основного текста. Оно не применяется к основному тексту страницы, заголовкам обычных карточек и секций, KPI (для них действует отдельная шкала §3.3), таблицам, кнопкам, поиску, формам, вкладкам, модальным окнам и полноэкранным состояниям.

### 3.3. Компактная типографика KPI операционных реестров

Эталоном является утверждённая плотная KPI-карточка реестра «Подрядчики». Одинаковые смысловые роли в операционных реестрах используют одну шкалу:

| Семантическая роль | Десктоп: размер / line-height | Мобильный: размер / line-height | Вес |
|---|---:|---:|---:|
| название показателя | `13 / 18px` | `11 / 13px` | `400` |
| значение | `24 / 28px` | `26 / 28px` | `700` |
| пояснение | `12 / 17px` | `11 / 13px` | `400` |

Эта шкала применяется только к компактной KPI-сетке операционного реестра. Она не заменяет показатели Главной, заголовки разделов, обычный текст, таблицы, кнопки или формы.

### 3.4. Обязательные правила

- основной текст не меньше `16px`; компактные служебные роли из §§3.2–3.3 являются единственными типографическими исключениями;
- длинный текст переносится внутри контейнера;
- многоточие допустимо только там, где полный текст доступен по клику;
- заголовок KPI не скрывается за `…`;
- нельзя уменьшать шрифт, чтобы содержимое «как-нибудь влезло»;
- иконка и текст имеют отдельные колонки и не перекрывают друг друга;
- одна и та же семантическая роль имеет одинаковый размер во всех модулях.

## 4. Сетка и каркас страницы

### 4.1. Мобильный контейнер

На ширине до `720px`:

- ширина страницы — `100%`;
- левый и правый отступ — `20px`;
- отсутствует горизонтальное переполнение страницы;
- нижний запас учитывает высоту нижней навигации и safe area;
- отрицательные внешние отступы запрещены, кроме отдельно согласованных горизонтальных каруселей.

### 4.2. Структура каждого мобильного раздела

```text
Мобильная шапка
↓ 24px
Заголовок раздела
↓ 8px
Описание
↓ 24px
Основные действия
↓ 16–24px
Рабочие секции
```

Все разделы должны использовать один и тот же каркас. «Клиенты», «Финансы», «Безопасность», «Обучение», «Подрядчики» и остальные модули не могут иметь разные внешние gutters и случайную ширину контента.

### 4.3. Нижняя навигация

- фиксирована у нижнего края;
- учитывает `safe-area-inset-bottom`;
- минимальная рабочая высота — `82px`;
- контент, модальные окна и подсказки не перекрываются навигацией;
- плавающий помощник находится над панелью и не закрывает её пункты;
- основное действие «Создать» является единой мобильной точкой создания, если на странице не требуется специально контекстное действие.

## 5. Карточки

### 5.1. Обычная карточка

```text
фон: white
граница: 1px solid var(--ah-border)
радиус: 22px
padding: 20px
тень: отсутствует или очень мягкая
```

Внутри карточки допускаются четыре смысловые области:

1. заголовок;
2. пояснение;
3. данные / состояние;
4. действие.

Каждая область не получает отдельную рамку или отдельную карточную геометрию.

### 5.2. KPI на Главной

Мобильная Главная использует горизонтальную ленту полноценных карточек.

```text
ширина карточки: 240–260px
минимальная ширина: 220px
минимальная высота: 142px
gap: 12px
видно: одна полная карточка + часть следующей
```

Структура карточки:

```text
иконка 42×42
название показателя
значение
короткое состояние
```

Карточка не может сжиматься в узкую вертикальную капсулу. Шесть узких колонок на ширине телефона запрещены.

### 5.3. Компактные KPI операционных реестров

Подрядчики, юридический контур, бухгалтерия и другие операционные реестры используют одну семантическую KPI-роль.

| Режим | Колонки | Gap | Min-height | Padding | Радиус |
|---|---:|---:|---:|---:|---:|
| шире `1024px` | `4` | `12px` | `98px` | `16px` | `16px` |
| `721–1024px` | `2` | `12px` | `98px` | `16px` | `16px` |
| `360–720px` | `2` | `11px` | `84px` | `11px 12px` | `13px` |
| до `359px` | `1` | `11px` | `84px` | `11px 12px` | `13px` |

Геометрия и типографика задаются только токенами `--ah-registry-kpi-*`. Локальные числовые копии этих значений запрещены.

Главная и иные специально согласованные обзорные KPI сохраняют собственный паттерн; компактная роль реестра к ним не применяется.

### 5.4. Информационные карточки

Информационный блок:

- одна поверхность;
- один радиус `22px`;
- один внутренний отступ;
- допускается тонкая цветная линия или мягкий фон состояния;
- текст внутри не оборачивается в отдельные рамки.

## 6. Пустые состояния

Все разделы используют единый компонент `EmptyState`.

Компонент имеет две плотности: `default` для самостоятельного состояния раздела и `compact` для встроенного состояния рабочего блока. Только `compact` использует служебную шкалу §3.2.

```text
одна карточка
один заголовок
одно пояснение
не более одного основного действия
```

Пример:

```text
Подрядчиков пока нет

Они появятся после загрузки первой подтверждённой банковской операции.

[Подключить банк]
```

Запрещено:

- рамка вокруг заголовка;
- рамка вокруг пояснения;
- пустая овальная кнопка;
- карточка внутри карточки;
- огромное белое поле без композиции;
- замена всего функционального раздела одной заглушкой.

Пустой раздел сохраняет вкладки, фильтры, действия и рабочую структуру.

## 7. Поля, поиск и формы

### 7.1. Универсальный контрол

```text
высота: 56px
радиус: 16px
шрифт: 16px
padding-left: 16px либо 52px с иконкой
padding-right: 16px либо 52px с подсказкой
```

### 7.2. Поиск

- используется единая SVG-лупа системы;
- размер лупы — `22–24px`;
- лупа располагается слева в отдельной зоне;
- текст начинается после зоны иконки;
- при наличии inline-help значок `?` размещается справа;
- лупа и `?` никогда не накладываются;
- текстовый символ `⌕` вместо SVG-иконки запрещён;
- невидимых кликабельных областей нет.

### 7.3. Формы

- подпись находится над полем;
- обязательность видна до отправки;
- пояснение располагается под полем;
- ошибка не изменяет геометрию всей формы;
- кнопки сохранения доступны на мобильном без прокрутки за нижнюю навигацию;
- данные не сохраняются случайно при закрытии модального окна.

## 8. Кнопки

### 8.1. Основная

```text
height: 48–52px
radius: 16px
background: var(--ah-primary)
text: white, 16px, 600
```

### 8.2. Вторичная

```text
background: white
border: 1px solid var(--ah-border)
text: var(--ah-text)
```

### 8.3. Мобильные правила

- одна основная кнопка может занимать всю ширину;
- две равнозначные кнопки — две колонки;
- три и более действия не сжимаются в одну строку, а переходят в сетку или меню;
- текст не выходит за границы;
- минимальная touch-зона — `44×44px`;
- дублирующие действия на одном экране запрещены.

## 9. Вкладки

Мобильные вкладки:

- горизонтально прокручиваются;
- `gap: 20px`;
- первая вкладка начинается по общему gutter страницы;
- последняя имеет правый запас `20px`;
- активная вкладка подчёркнута;
- активная вкладка автоматически видна после загрузки;
- текст не обрезается посередине слова;
- вкладки не расширяют всю страницу по горизонтали.

Финансовые вкладки:

- Реестр;
- ДДС;
- ОПиУ;
- План и прогноз;
- Начисления и долги.

## 10. Финансовый период

Период является управляющим фильтром всего финансового модуля, а не отдельным информационным дашбордом.

### Мобильная структура

```text
Отчётный период                      Текущий месяц

[←]              [Август 2026]              [→]
```

Правила:

- верхняя строка: подпись слева, текстовое действие справа;
- нижняя строка: три элемента одинаковой высоты;
- стрелки — `48×48px`;
- центральный селектор занимает оставшееся пространство;
- нет дополнительной полноширинной фиолетовой кнопки;
- период применяется одновременно к Реестру, ДДС, ОПиУ, плану, прогнозу, начислениям и долгам;
- выбранный месяц допускается даже при отсутствии операций;
- период располагается перед KPI и не находится внутри огромной карточки.

## 11. Подсказки и обучение

В системе существуют две разные сущности.

### 11.1. Inline-help

Маленький `?` объясняет конкретное поле или действие.

- визуальный размер — `24px`;
- touch-зона — `44×44px`;
- всегда видим, если зона активна;
- если значка нет, кликабельной зоны тоже нет;
- располагается справа от подписи либо справа внутри поля;
- не использует координаты экрана;
- не переносится в случайный Portal;
- не уходит под соседний слой;
- не перекрывает лупу, текст или нижнюю навигацию.

### 11.2. Guided tour страницы

Большой фиолетовый `?` запускает пошаговое обучение по конкретной странице.

Для каждого шага вручную задаются:

- точный selector или устойчивый `data-help-block`;
- заголовок;
- что отображается;
- откуда поступают данные;
- что пользователь может сделать;
- что делать нельзя.

Запрещено:

- автоматически выбирать случайный `article`;
- выделять всю страницу как «рабочую область»;
- начинать обучение с приветствия;
- объяснять общий смысл вместо конкретного блока.

### Поведение на мобильном

- фон затемняется;
- подсвечивается один блок;
- callout появляется снизу над навигацией;
- максимальная высота — `45–55%` экрана;
- браузерный zoom не меняется;
- активное поле предварительно теряет фокус, клавиатура закрывается;
- прокрутка выполняется только если блок не виден;
- страница не центрируется без необходимости.

---

## 12. Модальные окна

### Десктоп

- центр экрана;
- ширина `720–880px` в зависимости от формы;
- радиус `28px`;
- overlay блокирует фон.

### Мобильный

- bottom sheet от нижнего края;
- ширина `100%`;
- верхние углы `28px`;
- максимальная высота `90dvh`;
- прокрутка внутри;
- верх не уходит под системную панель;
- действия не скрываются за нижней навигацией;
- модальное окно не появляется обрезанным сверху страницы.

---

## 13. Реестры и таблицы

Десктопная таблица не сжимается механически до ширины телефона.

На мобильном используется один из вариантов:

### Карточный реестр

```text
ID / статус
основное название
ключевые параметры
дата / сумма
действие
```

### Горизонтальная таблица

Используется только при необходимости сравнения колонок:

- собственный горизонтальный scroll;
- закреплённая шапка при необходимости;
- вся страница не прокручивается вбок.

## 14. Инженерные правила

### 14.1. Один источник стилей

Целевая структура:

```text
design-tokens.css
layout.css
components/
  Card
  KpiCard
  EmptyState
  SearchField
  Tabs
  PeriodSelector
  Modal
  HelpMarker
  GuidedTour
```

### 14.2. Запрещено

- создавать последовательные слои `mobile-v3`, `mobile-v4`, `mobile-v5`;
- дописывать CSS в конец файла build-time patch-скриптами;
- использовать селекторы `[class*=card]`, `[class*=empty]`, `[class*=panel]`;
- массово применять `!important`;
- описывать один компонент в нескольких конфликтующих файлах;
- исправлять production очередным CSS append;
- использовать отрицательные margin для компенсации неправильной сетки;
- создавать уникальную геометрию одного раздела без отдельного утверждения.

`!important` допускается только для переопределения сторонней библиотеки и сопровождается комментарием с причиной.

### 14.3. Компонентный принцип

Если два экрана показывают одинаковую сущность, они используют один компонент. Исправление общего компонента обязано исправлять все его экземпляры.

Обязательные общие компоненты:

- `PageContainer`;
- `SectionHeader`;
- `Card`;
- `CompactListCard`;
- `KpiCard`;
- `EmptyState`;
- `SearchField`;
- `Tabs`;
- `PeriodSelector`;
- `Modal` / `BottomSheet`;
- `HelpMarker`;
- `GuidedTour`.

## 15. Адаптивные режимы

| Режим | Ширина |
|---|---:|
| compact mobile | `320–374px` |
| standard mobile | `375–430px` |
| tablet | `431–1024px` |
| desktop | `1025–1919px` |
| large desktop | `1920px+` |

Каждый компонент имеет определённое поведение во всех режимах. Уменьшение ширины не должно приводить к автоматическому сжатию содержимого до нечитаемого состояния.

## 16. Обязательная визуальная проверка

Unit-тесты и успешная сборка не считаются визуальной приёмкой.

Каждое изменение проверяется минимум на:

| Устройство | Размер |
|---|---:|
| компактный iPhone | `375×812` |
| основной iPhone | `390×844` |
| крупный iPhone | `430×932` |
| планшет | `768×1024` |
| ноутбук | `1440×900` |
| рабочий монитор | `2560×1440` |

### Чек-лист приёмки

- отсутствует горизонтальное переполнение страницы;
- нет обрезанного текста;
- нет текста, прижатого к краю;
- одинаковые карточки имеют одинаковый радиус;
- нижняя навигация не перекрывает контент;
- поля имеют понятные иконки;
- отсутствуют невидимые активные зоны;
- пустой раздел сохраняет функциональность;
- модальные окна полностью доступны;
- guided tour подсвечивает правильный блок;
- мобильный экран не является ужатым десктопом;
- изменения проверены визуально, а не только тестами.

---

## 17. Критерий завершённости

Изменение считается завершённым только тогда, когда одновременно выполнены все условия:

1. компонент соответствует этому Design Code;
2. отсутствует локальная CSS-заплатка поверх другого слоя;
3. пройдены автоматические тесты;
4. выполнена визуальная проверка на обязательных разрешениях;
5. нет регрессии в соседних разделах, использующих тот же компонент;
6. production-ссылка проверена после фактического переключения версии;
7. владелец не видит расхождений с эталонной системой.

## 18. Приоритет внедрения

Переход на Design Code выполняется компонентно, а не по одному скриншоту:

1. общие токены и `PageContainer`;
2. `Card`, `CompactListCard`, `KpiCard`, `EmptyState` (`default` и `compact`);
3. `SearchField`, `Tabs`, `PeriodSelector`;

5. Главная;
6. Финансы;
7. Клиенты и семьи;
8. Подрядчики;
9. Безопасность;
10. остальные разделы системы.

До завершения общей компонентной базы новые визуальные patch-слои запрещены.

## 19. Неизменяемые решения владельца

- основной текст интерфейса — не меньше `16px`, кроме утверждённой компактной служебной роли `12/15`, `10/14`, `9/12`;
- модальные окна на десктопе открываются по центру, а не справа;
- на мобильном используется самостоятельная композиция;
- карточки и графики симметричны;
- графики занимают полезную ширину своей карточки;
- все разделы сохраняют функциональность при пустой базе;
- маленькие подсказки относятся к конкретному полю;
- большой помощник объясняет конкретные блоки страницы;
- одна сущность создаётся один раз и используется во всех модулях;
- визуальная система не может противоречить единой модели данных и прав доступа.
