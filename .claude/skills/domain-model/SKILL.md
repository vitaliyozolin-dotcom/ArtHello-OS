# Доменная модель ArtHello OS

По мотивам /domain-model с aihero.dev. Задача: любые изменения сущностей и связей делать осознанно относительно существующей модели, а не поверх неё.

## Источники истины (в порядке приоритета)

1. **`lib/db/src/schema/*.ts`** — фактическая модель (26 схем; barrel `schema/index.ts` — проверяй, что сущность реэкспортирована, иначе она вне миграций).
2. **`DATA_COVERAGE.md`** — какие данные реально покрыты и с какой provenance.
3. **`docs/integration_contracts.md`** — контракты внешних источников (AlfaCRM, банки, Google Sheets, SMSVizitka, Evotor).
4. `MASTER_BOOK.md` / `DECISIONS.md` — доменные правила и запреты.

Роли источников (принцип MASTER_BOOK): **банк = правда о движении денег, AlfaCRM = операционная правда.** Ни один не переопределяет другой в чужой зоне.

## Порядок работы

1. **Инвентаризация затронутого**: какие сущности/связи меняются; выпиши текущие определения из схем (таблица, ключи, FK, уникальности) — цитатами, не по памяти.
2. **Сверка с инвариантами домена**:
   - **Семьи/identity**: автослияние семей по одному слабому сигналу запрещено — только manual-review candidates. Идентификация по телефону идёт через normalizePhone (в проекте несколько расходящихся копий — риск PHONE из REFACTORING_PLAN.md; не добавляй новую).
   - **Leads vs students**: AlfaCRM leads (`is_study=0`) отделены от students и не попадают в student/family pipeline.
   - **Raw-слой**: `alpha_raw_records` append-only (D-036, триггеры на уровне БД); каждая нормализованная запись имеет реальный raw+batch FK. Новые нормализованные сущности обязаны наследовать это правило.
   - **Деньги**: целочисленные minor units; никакие ставки/KPI/статьи не выдумываются — неутверждённое остаётся `unresolved`.
   - **Юрлица**: карта «юрлицо → банковские счета → филиалы» — сущности с финансовым смыслом привязываются к юрлицу, не к «школе вообще».
3. **Модель изменения**: опиши новую/изменённую сущность — назначение, ключи, связи, источник данных и его provenance, что происходит при отсутствии данных (empty-state обязателен по DESIGN_CODE).
4. **Последствия**: какие миграции потребуются (→ скил `migration-check`), какие эндпоинты/страницы затронет, попадает ли в `permission-matrix.json` (роль/scope).
5. **Зафиксируй**: если изменение вводит новое доменное правило — предложи текст D-решения (следующий свободный D-номер) для DECISIONS.md.

## Отчёт

Мини-спецификация: сущности (было → станет), связи, инварианты, provenance каждого поля, открытые вопросы к владельцу (то, что нельзя вывести из источников — не домысливать).
