# Triage бэклога

По мотивам /triage с aihero.dev. Объект — `BACKLOG.md` (плюс сверка с `CURRENT_STATE.md`, `DECISIONS.md` и `REFACTORING_PLAN.md`).

Ключевое правило проекта: «файл существует ≠ ворота пройдены». Статус пункта подтверждается только доказательством в репо/CI, не памятью и не форматом чекбокса.

## Порядок

1. **Прочитай BACKLOG.md целиком.** Обрати внимание на легенду: `[x]` — заявлено сделанным, `[~]` — частично/ждёт независимого PASS, `[ ]` — открыт.
2. **Выборочная верификация `[x]` и `[~]`**: для каждого пункта, затрагивающего код — найди подтверждение (файл/тест/миграция/run). Особо проверяй пункты с оговоркой «закрыть только после независимого Reviewer PASS» — они НЕ закрыты, пока PASS не зафиксирован в docs.
3. **Ищи рассинхрон** с реальностью:
   - пункт открыт, но работа уже видна в репо (кандидат на закрытие с доказательством);
   - пункт закрыт, но условие деградировало (например, тест удалён/пропускается);
   - пункт дублирует находку REFACTORING_PLAN.md — связать, не плодить.
4. **Стейл-детекция**: пункты, ссылающиеся на исчезнувшие файлы/эндпоинты/workflow.
5. **Приоритизация**: предложи следующие 1–3 шага. Порядок приоритета проекта: security/доказуемость (P0) → надёжность платформы (P1) → операционная модель → финансовая правда → интерфейс (P2). «Приоритеты отражают ворота качества, а не желаемый порядок экранов» — цитата из BACKLOG.
6. **Не выдумывай пункты.** Новые пункты предлагай только из подтверждённых находок (аудит, упавшие тесты, открытые D-решения).

## Отчёт

- Таблица расхождений: пункт → заявленный статус → фактический статус → доказательство.
- Кандидаты на закрытие (с точным evidence, который нужно приложить).
- Стейл/дубли.
- Рекомендованные следующие шаги (1–3, с обоснованием приоритета).

BACKLOG.md сам не редактируй без явной просьбы — по правилам проекта его меняет Создатель после вердикта Ревизора.
