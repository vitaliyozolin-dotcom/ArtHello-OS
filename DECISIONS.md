# ArtHello OS — Decisions

## D-062 — Синхронизировать Точку по сохранённым настройкам без открытого браузера

Дата: 2026-09-08  
Статус: принято как реализация исходного поручения владельца о самостоятельной синхронизации счетов и реестра для ДДС  
Владелец: Исполнитель ArtHello OS

Node runtime запускает только ограниченный read-only исполнитель INT-T-TOCHKA через внутренний Miniflare dispatchFetch. Одноразовый служебный ключ создаётся в памяти процесса; он не возвращается пользователю, не хранится в Git/БД и не журналируется. Тело служебного запроса не может выбрать иное действие, подключение или платёж.

Автоматическая загрузка использует только уже сохранённые и подтверждённые компанию, юрлицо, разрешённые банком счета, дату начала и расписание. Lease, credentialGeneration, устойчивые statement IDs и атомарный commit исключают устаревший импорт и дубли. Явная пауза и отзыв/замена ключа блокируют дальнейшее исполнение; временная ошибка допускает ограниченный повтор с backoff. Неполная/отклонённая выписка не становится успешной синхронизацией и не обновляет last_success_at.

TOCHKA_AUTOSYNC_ENABLED=1 включается только у целевого production-контейнера после проверенного cutover. Clone/preflight и восстановленные копии данных остаются с выключенным планировщиком. Создание, подписание и отправка платежей запрещены. Неизменяемые банковские факты и ручная управленческая классификация из D-060 сохраняются.

Приёмка требует реального запуска без открытой страницы, сверки количества и сумм операций с банком, продолжения pending и повторного запуска без дублей. Локальные tests не заменяют эту приёмку. Модель одной настройки INT-T-TOCHKA не объявляется подключением нескольких неподтверждённых юрлиц.

## D-061 — Проверять релиз на отдельной машине сборки GitHub

Дата: 2026-09-08  
Статус: принято по явному поручению владельца вернуться к GitHub + собственной машине сборки и выпустить исправления  
Владелец: Исполнитель ArtHello OS

GitHub остаётся репозиторием и источником истории. Перенос в GitVerse приостановлен. Рассмотренный release-кандидат можно проверять до merge на отдельной одноразовой build-VM без production credentials, volumes, чужих host sockets, production private network и cloud control plane. Изоляция сети и удаление по TTL обеспечиваются внешним контроллером; название runner и самоописание JSON не доказывают изоляцию. Docker на builder остаётся root-эквивалентным.

Manual workflow-контроллер запускается из точного актуального main, проверяет exact SHA/tree фиксированной release-ветки codex/recovery-release-20260908 либо актуального main, и сверяет их с внешним provisioning record до checkout. Автоматический PR/PR-target не получает builder. Одна VM исполняет один job без повторного использования её диска. D-040 продолжает запрещать PR code на production runner.

Secret scan, Quality, PostgreSQL, migration/permission/visual proof, Verify v52 и проверки immutable image сохраняются. Provenance явно обозначает self-hosted-isolated-ephemeral. Production получает готовый образ через проверенную приватную доставку, затем обязательны clone-preflight, проверенная резервная копия, cutover, rollback guards и живая приёмка шести пользовательских сценариев. Успешная сборка не равна успешному выпуску.

Подготовка скриптов не означает наличия VM, административных полномочий регистрации runner или работающего artifact storage. Стоимость и приобретение нового сервера/хранилища не согласованы и не выполнялись. Старый одноразовый D-059 deploy не переиспользуется; новый consumer должен проверять фактический контракт собственной сборки. Данные и действующая версия сохраняются до доказанного безопасного cutover.

## D-060 — Банковский факт неизменяем, управленческое разнесение хранится отдельно

Дата: 2026-09-04  
Статус: принято владельцем в явном поручении слить PR №338, выпустить его в production и загрузить выписки Точки  
Владелец: Исполнитель ArtHello OS

Сумма, дата, направление, банковский контрагент, назначение и идентификатор операции из `bank_transactions` являются исходным банковским фактом и не изменяются при ручном разнесении. В `financial_operations` отдельно хранятся управленческие поля: статья ДДС, класс и статья ОПиУ, период начисления ОПиУ, управленческий контрагент и смысл операции. Изменение этих полей доступно только разрешённой финансовой роли и обязательно записывается в аудит.

Каждый путь открытия карточки операции, включая строки реестра и расшифровку ОПиУ, обязан заново инициализировать черновик данными именно выбранной операции. Повторное использование черновика другой операции запрещено, потому что может привести к бухгалтерски неверному разнесению при сохранении.

Изменение схемы выполняется только идемпотентной additive-миграцией: новые поля добавляются при отсутствии, существующие банковские и финансовые строки не удаляются. До production-активации обязательна проверенная резервная копия, после запуска — проверка целостности, сохранности финансовых данных и публичного health; при ошибке сохраняется автоматический откат.

Повторная загрузка выписок Точки выполняется read-only и идемпотентно по всем подтверждённым счетам за явно заданный период, с последующей сверкой количества операций и сумм поступлений/списаний с ответом банка. Правила автоклассификации повторяющихся платежей являются отдельным следующим этапом и не изменяют банковский факт.

Техническая метка релиза `D069` в именах patch/workflow — имя релизной задачи, а не номер архитектурного решения.

## D-059 — Исправить совместимость workerd service binding без перехода на OAuth

Дата: 2026-09-03  
Статус: принято как продолжение подтверждённого production-дефекта D-058; одноразовый release PR `#328` закреплён  
Владелец: Исполнитель ArtHello OS

D-058 опубликован production run `33762398372`: точный SHA `7e926f4c29aa7e3c3208a55451db035714861e28` активен, Node-контейнер получил ожидаемый защищённый HTTP 403 от Точки. Повтор владельца на `IMG_9996(2)`/`IMG_9997(2)` снова завершился сообщением «Не удалось связаться с Точкой». Воспроизведение на закреплённой Miniflare `4.20260515.0` установило причину: workerd не реализует `redirect: "error"` и отклоняет внутренний Request до вызова `TOCHKA_TRANSPORT`.

Внутренний worker → service binding hop использует `redirect: "manual"`, который принимает workerd. Это не разрешает банковские редиректы: Node-мост повторно проверяет официальный origin, точные read-only методы и пути и выполняет внешний `fetch` с `redirect: "error"`. Заголовки по-прежнему очищаются, платёжные пути запрещены, JWT не журналируется. Ответ Точки читается внутри 45-секундного таймаута и ограничивается 2 000 000 байт, поэтому задержавшееся или чрезмерное тело не может бессрочно удерживать запрос.

Переход на OAuth сейчас не выполняется. Ошибка возникает до банковской аутентификации, поэтому OAuth token exchange и последующие API-вызовы встретили бы тот же дефект транспорта. Кроме того, OAuth требует зарегистрированного приложения, `client_id`, `client_secret` и redirect URI; его следует пересмотреть при подключении сторонних компаний от имени клиентов, а не как обход этого сбоя.

Одноразовая выкладка разрешена только из `vitaliyozolin-dotcom/ArtHello-OS:codex/d059-tochka-binding-redirect-20260903` через PR `#328`, прямого потомка D-058 `7e926f4c29aa7e3c3208a55451db035714861e28`. Приёмка требует 8/8 transport/service-binding тестов, first-attempt exact-SHA Quality/Proof/Verify, production Node TLS egress, изолированный clone-preflight, backup-first cutover, rollback guards и публичный health-check. После релиза владелец повторяет подключение: допустимы либо реальные данные, либо конкретный HTTP-ответ банка о ключе/правах; общая транспортная ошибка недопустима.

## D-058 — Выполнять read-only запросы Точки через ограниченный Node service binding и не увеличивать форму на iPhone

Дата: 2026-09-03  
Статус: принято по повторному фактическому дефекту; одноразовый release PR `#327` закреплён  
Владелец: Исполнитель ArtHello OS

D-057 успешно прошёл hosted Quality/Proof/Verify и production deployment `33752514068`: отдельный Node‑контейнер подтвердил TLS‑доступ к Точке ожидаемым защищённым HTTP 403. Повторная проверка владельцем с реальным ключом всё равно завершилась общей ошибкой «Не удалось связаться с Точкой». Это отделяет доступность Node от фактического пути приложения: API‑маршрут исполняется внутри Miniflare/workerd, чей `fetch` не использует Node `NODE_EXTRA_CA_CERTS`. Скриншоты `IMG_9991`/`IMG_9992` также подтверждают автоприближение iOS после фокуса на поле ключа с размером шрифта 13 px.

Только четыре документированных read-only вызова Точки передаются из worker в Node через function-valued Miniflare service binding: клиенты, счета, создание отчёта-выписки и чтение готовой выписки. Мост принимает только официальный origin, точные методы и пути, JWT Bearer, ограниченный JSON выписки; удаляет cookie/forwarded и лишние ответные заголовки, запрещает query, redirects, чужие origin и все платёжные пути. Ключ не журналируется. Production preflight вызывает экспорт того же модуля без ключа, а Docker image явно содержит этот модуль. Мобильные `input/select/textarea` мастера получают 16 px — это устраняет автозум Safari без запрета пользовательского масштабирования.

Одноразовая выкладка разрешена только из `vitaliyozolin-dotcom/ArtHello-OS:codex/d058-tochka-node-bridge-ios-20260903` через PR `#327`, являющийся прямым потомком production‑коммита `1cdca3fd9cb63f6dd7c8d8ce137e4126b4fc1123`. Завершение требует целевых transport/UI тестов, first-attempt hosted Quality/Proof/Verify точного SHA, `ARTHELLO_TOCHKA_TLS_EGRESS=VERIFIED` из реального transport-модуля, изолированного clone-preflight, backup-first cutover, rollback guards и публичного health-check. Фактическое принятие ключа и импорт банковских данных подтверждает владелец после релиза; ответ 401/403 банка не считается транспортной ошибкой и должен отображаться отдельно.

## D-056 — Проверять X.509 Точки внутри immutable runtime, а не на production-host

Дата: 2026-09-03  
Статус: принято как fail-closed продолжение порученного D-055; одноразовый release PR `#325` закреплён  
Владелец: Исполнитель ArtHello OS

GitHub-подписанный squash merge D-055 `66ca9490d7e765a1338ad0c4ce8cdc2c163c9d36` прошёл повторные Quality, Proof и Verify на `main`. Полная X.509-проверка CA-признака, самоподписи, срока и fingerprint уже выполняется при hosted Docker build; активный trust store повторно проверяется процессом Node внутри запущенного immutable container; реальный TLS-выход к официальному read-only endpoint Точки проверяется тем же контейнером до остановки live. Verify workflow теперь отдельно запрещает host-вызов Node в checkout-contract.

Одноразовая выкладка разрешена только из `vitaliyozolin-dotcom/ArtHello-OS:codex/d056-tochka-runner-preflight-20260903` через PR `#325`, являющийся прямым потомком D-055 `66ca9490d7e765a1338ad0c4ce8cdc2c163c9d36`. Завершение требует нового первого attempt hosted Quality/Verify, production `ARTHELLO_TOCHKA_TLS_EGRESS=VERIFIED`, backup-first cutover, rollback guards и публичного health-check.

Владелец: Исполнитель ArtHello OS

До остановки действующего контейнера clone-preflight временно подключается к production-сети и без ключа, Authorization или иных секретов обращается к официальному read-only endpoint Точки. Окно «Настройки» и вложенная форма «Банк Точка» являются двумя независимыми слоями. Одноразовая выкладка разрешена только из `vitaliyozolin-dotcom/ArtHello-OS:codex/d054-tochka-modal-scroll-20260903` через PR `#321`, являющийся прямым потомком production-коммита `1038a1960aaf62f57a161d8a16c804161a7f6c53`.

## D-053 — Прокручиваемое окно Точки и полный read-only импорт банковского факта

Дата: 2026-09-03  
Статус: принято владельцем в явном поручении продолжать до production-релиза

Окно настройки интеграции использует фиксированные заголовок и нижние действия, а длинная центральная часть прокручивается независимо внутри динамической высоты экрана. На мобильном устройстве поля, официальный документ и кнопки остаются достижимыми; касание внутри формы не закрывает окно.

После проверки ключа и выбранной компании ArtHello OS выполняет документированный read-only поток Точки: получает доступные счета, запрашивает формирование выписок и читает готовые выписки по каждому разрешённому счёту. В систему сохраняются маскированные счета и остатки, реестр выписок и проведённые операции. ## D-043 — Главная, доступы, единые карточки и банковские подключения следуют фактической ответственности пользователя

Дата: 2026-09-02  
Статус: принято владельцем в явном поручении на production-релиз; уточняет D-006, D-014, D-023 и D-033

Главная ArtHello OS является рабочим дашбордом, а не фиксированной витриной. Её состав по умолчанию определяется фактической ролью; пользователь может выбрать виджеты, изменить их порядок и размер и вернуть ролевую раскладку. Раскладка сохраняется для сочетания пользователя и роли. Владелец получает полный операционный обзор и право на настройку, но отсутствие данных не заменяется выдуманными показателями. Запрещена общая CSS-сетка, которая превращает все блоки Главной в две колонки и растягивает пустые карточки на высоту экрана.

Меню, избранное, поиск разделов и прямые переходы используют одну карту эффективных разрешений. Недоступный роли раздел не показывается; прямой URL к нему завершается fail closed и возвращает пользователя на доступную Главную. Владелец является высшей системной и конфигурационной ролью: он управляет ролями, интеграциями и их разрешениями. Медицинские данные остаются отдельным чувствительным контуром и не открываются одним фактом владения; владелец назначает такой допуск отдельной роли медработника.

У вручную созданной единой карточки нет внешнего проверяющего и статуса «качество». Такая карточка честно помечается «Создано вручную». Очередь «Требует сверки» появляется только при доказанном конфликте, дубле или импортированном источнике, которому действительно требуется решение человека; интерфейс явно сообщает причину и кто должен принять решение. История происхождения и проверки сохраняется.

JWT/API-секрет Точки вводит сам владелец в замаскированном поле ArtHello OS при настройке подключения. Сначала кандидат проверяется безопасной read-only цепочкой банка, и только после успешной проверки несекретная привязка и зашифрованный секрет сохраняются атомарно. Значение не возвращается клиенту, не попадает в логи и хранится как AES-256-GCM envelope в локальной production-БД; отдельный runtime master key не записывается в БД или репозиторий. Перепривязать, ротировать, применить или отозвать банковский credential может только канонический владелец. Подключение относится к подтверждённому банковскому customerCode существующего юридического лица, а не к филиалу или одному счёту: один ключ может обслуживать все счета, разрешённые этим ключом у провайдера. Счета сопоставляются с филиалами отдельно; один счёт может принимать поступления нескольких направлений, поэтому распределение допускается на уровне операции, а неоднозначные операции остаются в очереди классификации. Если другое юрлицо не входит в разрешения ключа, для него требуется отдельное подключение — не отдельный ключ на каждый локальный филиал или счёт.

Декоративные знаки вопроса из формы подключения удаляются. Критичные пояснения остаются обычным доступным текстом рядом с полем. Приёмка требует поведенческих тестов ролевого меню, прямого URL, персональной раскладки, происхождения карточек и owner-only обработки секрета, успешной сборки и браузерной проверки точного production-кандидата под владельцем и ограниченной ролью. На живом адресе после cutover отдельно проверяются публичная поверхность, аутентификационная граница и неизменность School; реальные пароли и JWT в CI не передаются. Проверка одних строк или CSS-селекторов не считается доказательством корректной раскладки.

Одноразово для релиза PR `#310` из `vitaliyozolin-dotcom/ArtHello-OS:codex/owner-dashboard-tochka-20260902` D-040 уточняется только в части запуска: явное поручение владельца в текущей задаче является авторизацией выпуска, а вместо недоступного `workflow_dispatch` используется `workflow_run` после успешной hosted-проверки `Verify ArtHello v52 release` на точном подписанном squash-коммите, который в момент каждого необратимого шага остаётся текущим `main`. Environment `production-ru` остаётся обязательной платформенной границей, но наличие отдельно настроенного required reviewer не заявляется без проверяемого доказательства. Ограничения конкретного PR, владельца, репозитория, ветки, actor и первого attempt исходной Verify-проверки, точные Quality и Verify gates, изоляция self-hosted runner, backup-first cutover и автоматический rollback остаются обязательными. Повтор успешной выкладки того же SHA и повторный attempt production-run запрещены. Это исключение не распространяется на следующие релизы.

## D-044 — Fail-closed recovery после отказа импорта проверенного образа

Дата: 2026-09-02

## D-047 — Procfs D1-дескрипторы проверяет тот же непривилегированный runtime user

Дата: 2026-09-02  
Статус: принято владельцем в рамках явного поручения завершить production-релиз; одноразовый recovery PR `#314` закреплён

Production-run D-046 `33687247475` подтвердил exact main, Quality/Verify, архив, evidence, Docker import и переносимый runtime fingerprint, затем остановился на первом metadata-only FD gate до pause, snapshot, копирования, запуска clone, остановки live, backup или изменения Caddy. Rollback снова подтвердил здоровье неизменённого старого production. Канонический D1 path и inventory D-046 остаются правильными.

Причина — FD scanner запускался через `docker exec --user 0:0`, тогда как PID 1 и workerd работают под `node`. Production-контейнер намеренно не получает `CAP_SYS_PTRACE`; procfs ptrace access может запретить container-root читать ссылки `/proc/<pid>/fd` процесса другого UID. Это дало ложный отказ до появления разрешающего маркера.

Scanner теперь выполняется стандартным пользователем контейнера, до чтения проверяет, что его UID непривилегированный и совпадает с UID PID 1, затем применяет неизменный allowlist канонического D1/WAL/SHM и запрещает иной открытый non-metadata D1. При отказе в журнал выводятся только роль этапа, безопасная причина и агрегатные количества; пути, строки БД, credential и идентификаторы пользователей не выводятся. Hosted gate отдельно запрещает возврат `--user 0:0` в этой функции и требует проверки same-UID, non-root и rejection diagnostics.

Одноразовое исключение закреплено только за PR `#314` из `vitaliyozolin-dotcom/ArtHello-OS:codex/same-user-d1-fd-recovery-20260902`. Все требования D-043–D-046 к exact PR/actor/main SHA, первому attempt, Quality/Verify, protected Environment, provenance образа, canonical inventory, backup-first cutover и rollback сохраняются; повтор старых run запрещён.

## D-050 — Персональное рабочее пространство, понятный учёт и управляемые интеграции

Дата: 2026-09-03  
Статус: принято владельцем в явном поручении исправить перечисленные сценарии и выпустить результат; одноразовый release PR `#317` закреплён

Карточки пользователей отображают основные сведения и статусы в одной–двух строках, а должность при создании вводится свободно. Шаблон роли только предварительно отмечает разрешённые разделы: владелец обязан иметь возможность вручную снять или добавить каждый допустимый доступ до сохранения. «Интеграции» и «Доступы» находятся в настройках, а состав «Избранного» хранится отдельно для каждого пользователя и не расширяет его эффективные права.

Окна интеграций являются рабочими формами, а не демонстрационными карточками: поля, переключатели и действия доступны с клавиатуры и мышью, ошибки объясняются рядом с причиной. «Альфа-Банк» заменён на read-only подключение «Т-Банк» по официальному Open API; выпуск не получает права создавать платежи. JWT проверяется сервером, секреты не возвращаются в браузер, а при настроенном банком IP allowlist исходящий публичный IP должен совпасть с явно заданным владельцем значением. Подключение «Точки» сохраняет существующие owner-only и read-only ограничения.

Вход в электронный дневник использует только доверенные HTTPS origins ArtHello OS и School. Центральный секрет извлекается при выпуске из единственного работающего контейнера School, передаётся ArtHello OS только через read-only secret file и не записывается в репозиторий, GitHub secrets, environment или логи. Синхронизация прав и семей выполняется через durable outbox с идемпотентным event id, lease, CAS и сохранением порядка ревизий; владелец может безопасно повторить неуспешную доставку.

Сканы договоров сначала проходят ограниченную по типу и размеру серверную обработку, затем распознанный результат открывается как редактируемый черновик и сохраняется только после явного подтверждения пользователя. Ключ OCR/генерации изображений допускается только как runtime secret file. Понятные номера вида «Задача №1» и «Договор №0001» являются интерфейсными метками; внутренние идентификаторы остаются техническими ключами и не показываются пользователю без диагностической необходимости. «Приёмка» объясняет назначение и ответственного, а жизненный путь строится только для явно выбранного сотрудника.

Приёмка требует линтера, production-сборки, полного набора тестов, hosted Quality и Verify на точном squash-коммите, неизменяемого Docker image, изолированного clone-preflight, резервной копии до cutover и автоматического rollback. Одноразовый выпуск закреплён только за PR `#317` из `vitaliyozolin-dotcom/ArtHello-OS:codex/owner-workspace-integrations-20260903`. Production workflow обязан проверить exact repository, branch, PR, actor, первый attempt исходной Verify-проверки и актуальность SHA в `main`; повтор успешной выкладки того же SHA запрещён. Отсутствующие необязательные ключ OpenAI или подтверждённый T-Банком egress IP не подменяются тестовыми значениями: соответствующая возможность остаётся явно не настроенной.
